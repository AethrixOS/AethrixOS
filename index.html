$ aethrix --about

Not a distribution. A foundation.

Most "new" operating systems are Linux with a different wallpaper. AethrixOS is not that. The bootloader, kernel, network stack, filesystem and shell are original code — no forked kernel, nothing borrowed.

It's shared publicly for study and experimentation, not as an open-source project. See the license below before you redistribute anything.

$ aethrix --features

What actually works today.

Custom bootloader

Two-stage boot, 16 → 32-bit shipped. The 32 → 64-bit long-mode chain is in progress.

Kernel core

VGA console, PS/2 keyboard, ATA PIO disk driver, PCI enumeration.

Full network stack

Ethernet, ARP, IPv4, ICMP, UDP, DHCP, DNS, and an 11-state TCP implementation.

Flat filesystem

Parent-directory pointers, persisted to disk. Variable-size files land in v0.5.0.

Multi-user shell

~40 built-in commands, root role, multi-user login.

NIC drivers

RTL8139, AMD PCnet and Intel E1000 — verified end-to-end with real DHCP, DNS and HTTP.

Inside v0.1.0 — shipped ›

Kernel core

  • VGA text console at 0xB8000 — colors, cursor, scroll
  • PS/2 keyboard with shift, control, caps lock
  • ATA PIO disk driver
  • Flat filesystem with parent-directory pointers, persisted to disk
  • Multi-user login with root role, shell with ~40 built-in commands
  • PCI enumeration via 0xCF8/0xCFC

Network stack

  • Ethernet II framing and dispatch
  • ARP with cache, request, reply, aging
  • IPv4 receive, send, header checksum, gateway routing
  • ICMP echo request/reply, UDP with pseudo-header checksum
  • DHCPv4 full DORA state machine
  • DNS A-record resolver with TTL cache

Transport layer

  • TCP 11-state machine, sequence numbers with wraparound
  • Retransmission queue with exponential backoff
  • FIN/RST handling, TIME_WAIT, 16-entry connection table

NIC drivers

  • RTL8139 (QEMU), AMD PCnet (VirtualBox), Intel E1000 (both)

Verified end-to-end

  • DHCP lease, DNS resolution of real hostnames
  • ICMP ping to LAN and internet hosts
  • TCP connection to public servers, HTTP GET returning a real page
64-bit build — same version, different architecture ›
  • Custom MBR bootloader, no GRUB — two-stage 16 → 32 → 64-bit chain
  • A20 enable, GDT setup, page-table construction
  • Identity map of the full 4 GB, covering all MMIO BARs
  • Long mode (IA-32e) entry, 64-bit kernel entry stub
  • Kernel compiled with gcc -m64 -ffreestanding, no libc, no malloc
  • SSE disabled at compile time; CR4.OSFXSR/OSXMMEXCPT enabled for safety
  • Boots to login on QEMU and VirtualBox; full network-stack verification is still ongoing
Inside v0.2.0 — next, planned ›

Interrupts

  • 256-entry IDT, stubs for all 32 exceptions and 16 IRQs, PIC remap
  • PIT at 100 Hz, keyboard IRQ1, kernel panic handler with full register dump

Password security

  • SHA-256, HMAC-SHA-256, PBKDF2 with 100,000 iterations, per-user salt
  • Disk format bump from AETHRX1 to AETHRX2

Shell and permissions

  • UID model, per-file owner and mode, su/sudo/chmod/chown
  • Shell syntax: &&, ||, $VAR, quoting, comments, persistent history

Cross-cutting work

SecurityInput validation, memory safety, privilege separation, regular audits.
TestingUnit tests, protocol tests, negative tests, fuzzing, benchmarks.
DocumentationOne document per subsystem, public API and design decision.
PortabilityArchitecture-specific code stays in arch/; everything above is arch-independent.

Design contracts

  • No libc, no malloc in the kernel — every allocation is static
  • All IPv4 addresses in canonical little-endian form, one representation everywhere
  • Single-threaded kernel, no locks, until the scheduler lands
  • Weak symbol dispatch between protocol layers
  • No dynamic linking, no Python in build steps

Dates are targets, not promises — solo-developer pace, one commit at a time.
